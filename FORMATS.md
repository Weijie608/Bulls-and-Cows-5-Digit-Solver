# Strategy and Result File Formats

The original three files live in `optimized_20260925_052028/`. They are retained
byte-for-byte. `publication.py` reads them and produces the tree, summary and
checksums in the same snapshot directory for distribution.

## Codebook

The canonical codebook is generated by
`itertools.permutations("0123456789", 5)` in lexicographic order. IDs range from
0 to 30,239. ID 0 is `01234`. All codes are strings, so leading zeroes are retained.

For the codebook SHA-256, encode each code as ASCII followed by one LF byte,
with no spaces or header. Concatenate all 30,240 lines before hashing.

## Candidate sets

A candidate set is a 30,240-bit bitset occupying exactly 3,780 bytes.
Code ID `i` is bit `i % 8` of byte `i // 8`, least significant bit first.
A state's SHA-256 is computed from these uncompressed bytes.

## SQLite

The database contains exactly the tables `strategy` and `metadata`.
The strategy columns, in order, are:

| Column | Meaning |
| --- | --- |
| `state_hash` | SHA-256 of the uncompressed bitset, stored as 32 binary bytes. |
| `candidate_bits_z` | The bitset compressed with zlib. |
| `candidate_count` | Number of set bits. |
| `guess_id` | Canonical codebook ID of the selected guess. |

The `metadata` table has columns `key` and `value`, with keys
`codebook_sha256`, `step_distribution`, `results_sha256`, `record_count` and
`created_utc`. Distributions and counts concern strict success through `5r5s`.
The stored creation timestamp concerns the source snapshot, not a GitHub release.

The database contains all 8,600 reachable non-singleton decisions and all
30,240 singleton decisions. Some singleton decisions are unnecessary in play
because their secrets have already been guessed. Database rows are therefore
not in one-to-one correspondence with explicit success-tree nodes.

## Base85 export

Read the ASCII file, remove ASCII whitespace, apply Python's `base64.b85decode`,
then zlib-decompress the decoded bytes. This is Base85, not Ascii85.

The decompressed payload consists of:

| Bytes | Content |
| --- | --- |
| 0–7 | ASCII magic `BCS7SUM1`. |
| 8–11 | Number of records, unsigned 32-bit big-endian integer. |
| 12 onward | Fixed-size records, each 3,785 bytes. |

Each record contains a 3,780-byte candidate bitset, then a 2-byte candidate
count, 2-byte guess ID and 1-byte tag. The numeric trailer is decoded with
`struct.unpack(">HHB", trailer)`. All retained records have tag `1` and
candidate count greater than one. The tag is a format field, not a claim of
optimality. A singleton is handled by guessing its sole candidate.

There are 8,600 records and 32,551,012 decompressed bytes. Record order is not
significant; duplicate candidate sets are invalid. `decode_strategy()` in
`publication.py` is the reference decoder. Its return value is a mapping from
raw candidate bitsets to guess IDs. It requires no access to the development
repository or the historical optimizer.

## Per-secret results

Each line is `<secret><space><success_count><LF>`, ASCII, with exactly one space.
There is no header. There are 30,240 lines, in canonical codebook order.
Hash the bytes exactly, including the final newline. `.gitattributes` preserves
LF endings when checked out on Windows.

## Explicit success tree

`strategy_tree.json` is a JSON object with format `bac5-success-tree-v1`,
`root: 0`, a feedback description and a `nodes` array. Each node occupies one
physical line. A node's integer `id` is its index in that array. Nodes are
numbered by depth-first traversal; branches are ordered by `(r, s)`.

A **guess node** has `kind: "guess"`, `depth`, `candidate_count`, `guess`,
`state_sha256` and `branches`. The root has depth 0. Depth counts guesses already
made before the node's next guess. The state's candidates can be reconstructed
by applying the feedback on the path from the root to the full codebook.

Each branch has `feedback: [r, s]` and `child`, an integer node ID. Only non-empty
feedback buckets appear. The impossible answer `[4, 5]` never appears.

A **success leaf** has `kind: "success"`, `depth`, `secret` and
`identification_count`. Its depth is the success count. Every success leaf is
reached by `[5, 5]`. A non-winning branch leaving one candidate leads to a
singleton guess node, whose sole `[5, 5]` branch leads to a success leaf one
level deeper. This prevents identification from being mistaken for success.

To follow a secret, start at node 0, calculate feedback against each node's
`guess`, and follow the matching branch until a success leaf. Alternatively,
follow a supplied truthful feedback sequence. The terminal `secret` must match
the secret being followed. See the independent all-secret traversal in
`tests/test_publication.py`.

This tree has 61,102 nodes and exactly 30,240 success leaves. It is an explicit
success tree, while the identification tree defined in `CONCEPTS.md` stops at
the first singleton. Their heights are 7 and 6, respectively.

## Summary and checksums

`summary.json` uses format `bac5-publication-summary-v1`. The `success` and
`identification` objects each include a maximum, total, exact mean numerator
and denominator, floating-point display value, and a distribution keyed by
decimal count strings. The exact fraction is authoritative; the decimal is
only a display approximation. Other fields describe rules, record counts,
tree size, original file hashes and the scope of the claims.

`SHA256SUMS` contains `<lowercase SHA-256><two spaces><filename><LF>` lines,
sorted by filename. Paths are relative to the snapshot directory. It covers
the three original artifacts, the tree and the summary; it does not cover
itself or repository source files. It detects byte changes, not authorship.

Derived files use ASCII and LF and contain no runtime timestamp, absolute
machine path or elapsed time. This makes exports reproducible byte-for-byte.
